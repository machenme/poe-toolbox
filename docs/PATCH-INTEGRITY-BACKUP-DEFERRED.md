# 补丁完整性与操作级备份讨论记录

## 当前结论

本轮暂不实现“每次操作只备份受影响内容，并在任意失败后自动恢复”的新事务备份方案。先保留现有已经完成的补丁事务化能力，后续再单独设计、实现和验证操作级备份。

本轮重点是游戏文件完整性，不优先扩展安全防护能力。目标是尽可能避免补丁失败后破坏游戏数据，而不是防止用户主动替换程序文件。

## 已确认的项目方向

- 应用和还原尽量在内存中完成，最后只保存一次。
- 任意异常都不应留下半完成的补丁状态。
- `AddFile` 的补丁流程禁止使用自动保存版本。
- `addfile-derived` 校验源文件和目标文件 SHA-256，避免覆盖其他 Mod。
- 应用补丁前拒绝游戏正在运行。
- 背包清理属于独立的运行态流程，不与静态补丁写入混用。
- 区分“撤销引用”和“彻底清理补丁文件”。
- 支持孤儿 Bundle 清理。
- foreign reference 哨兵逻辑必须保证 apply/revert 成对可逆。
- 程序继续要求管理员权限，安装目录可能位于 `Program Files`，游戏运行时的相关清理操作也需要管理员权限。
- 暂不加入 GitHub Actions commit SHA 固定和发布 ZIP SHA-256 文件。

## 已完成的相关实现

- apply/revert 已采用内存事务模型，正常情况下只保存一次。
- 异常退出时会丢弃尚未保存的 Bundle 缓冲。
- 补丁流程已有索引字节快照和内存 `MutationSnapshot` 回滚。
- 新建补丁 Bundle 会在失败时清理。
- 保存后会重新打开索引并检查目标状态。
- `GameDataLoader`、`GameDataAccess` 的主要写入口会检查游戏是否运行。
- 已补全 PoE 进程名，包括 Steam/KG 变体。
- purge 重建目录表时保留 Murmur/FNV 根哈希，并从原始目录 Bundle 重建路径。
- purge 只移除补丁自己新增的路径（`addfile-derived` 的副本、`addfile-asset` 的新增文件）；按前缀无差别删除会连游戏原有文件的记录一起删掉——还原补丁会把被改过的原版文件内容重定向进补丁 Bundle，那些记录是客户端唯一的内容来源。
- 补丁 Bundle 名由执行时间戳改为补丁版本号（`PATCHED/<bundleName>_v<version>`），反复 apply/revert 复用同一个文件，不再堆积。
- Schema 下载限制为 16 MiB，并校验 JSON 结构。
- 更新元数据限制为 256 KiB，并校验 HTTPS URL、版本和 SHA-256 格式。
- 当前验证结果：Release build 通过；测试 50 项通过。

## 新规则：只备份本次实际受影响的内容

用户确认的规则是：

> 所有对原始文件的操作之前，必须先备份一个原始文件再操作；任何失败都恢复到操作前状态。备份范围只包括本次操作实际会影响的内容，不备份整个游戏目录。

这里的“受影响内容”包括：

1. 本次操作会修改的逻辑文件原始字节。
2. 本次操作会修改或删除的索引原始字节。
3. `cleanup/purge` 可能删除或重写的 Bundle。
4. 需要恢复的路径、长度和 SHA-256 指纹。

备份失败时必须在任何游戏数据写入前中止。

## 推荐的后续实现方案

### 1. 操作级 before-image

不要复用长期 baseline 作为回滚点。每次操作开始时创建唯一的临时操作目录，保存：

- 原始索引快照。
- 本次 patch 声明涉及的逻辑文件快照。
- 可能被删除或覆盖的 Bundle 快照。
- 每份快照的长度和 SHA-256。

长期 baseline 仍可用于用户主动恢复，但不能替代本次操作快照，以免把旧版本游戏数据恢复到新版本客户端。

### 2. apply/revert

在执行 patch operation 前，根据 operation 类型计算受影响路径：

- `addfile-derived`：源文件和目标文件。
- `addfile-asset`：目标文件。
- `patchptr-byid`：目标表文件。
- `edittext`：目标文本文件。

备份完成并校验后才允许进入写入阶段。失败时恢复索引和相关 Bundle，重新打开索引并验证所有受影响文件的指纹。

### 3. cleanup/purge

这两类操作必须使用独立的删除事务：

- 先将直接文件 Bundle 移入同盘隔离目录，避免复制整个 Bundle。
- 索引提交成功并重新打开校验后，再删除隔离目录。
- 失败时把隔离文件移回原位置。
- 对 GGPK 内嵌 Bundle，需要提供记录级恢复能力；不能假设恢复 `_.index.bin` 就能恢复整个容器。

### 4. 成功与失败边界

- 只有保存成功、重新打开成功、受影响文件指纹全部匹配后，才删除临时备份。
- 审计日志失败不应回滚已经成功提交的游戏数据，但必须记录警告。
- 备份恢复失败时保留临时备份，并明确提示用户，不得静默删除。

## 工作量与性能预估

工作量为中等，主要集中在事务边界、Bundle 恢复和异常测试，不需要重写补丁引擎。

- 普通 apply/revert 通常只增加一次原始文件读取和 SHA-256 计算，预计增加几百毫秒到几秒。
- 只备份少量逻辑文件时，不会明显增加操作时间。
- `cleanup/purge` 涉及大量 Bundle 时，复制会明显变慢，因此优先采用同盘移动到隔离目录。
- GGPK 的记录级恢复复杂度明显高于 Bundles2 目录模式，是后续实现的主要风险点。

## 当前已知风险

- 直接 `_.index.bin` 的原地保存仍存在进程崩溃或断电导致部分写入的风险，当前虽使用临时替换的外部写入口，但 `Index.Save()` 本身仍需进一步审查。
- cleanup/purge 尚未具备与 apply/revert 同等级的完整恢复事务。
- 长期 baseline 不随游戏版本自动变化。
- “检查游戏未运行”与实际保存之间仍存在启动竞态，只能在打开和保存阶段分别检查来降低风险。
- GGPK 的 Bundle/容器级回滚不能简单等同于恢复内部索引。

## 暂缓原因

当前先不开发这一部分，避免在没有覆盖 Bundles2、GGPK、删除 Bundle、进程中断和恢复失败场景之前，把半成品事务逻辑接入所有写入口。后续恢复开发时，应先补齐设计和测试，再逐步接入 apply/revert，最后接入 cleanup/purge。
